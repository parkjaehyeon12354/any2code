# 프로젝트 개발 세부 내용 (1~3)

---

## 1. 개발배경 및 목적

중학교 때부터 고등학교에 올라오기까지, 과학 성적이 조금씩 떨어지는 것을
스스로 느꼈습니다. 원인을 찾아보려고 그동안 치른 시험지를 모아 틀린 문제를
유형별로 나눠 보았습니다.

결과는 뚜렷했습니다. **이론을 묻는 문제는 대부분 맞혔지만, 실험 결과를
해석하고 도출하는 문제에서는 시간을 오래 쓰고도 결국 틀리는 경우가 많았습니다.**

원인은 지식의 부족이 아니라 **경험의 부족**이었습니다.
교과서로 "이 조건을 바꾸면 이런 결과가 나온다"는 문장은 외웠지만,
정작 그 조건을 직접 바꿔 본 적이 없었기 때문입니다.
학교 실험은 준비물과 시간, 안전 문제로 한 학기에 몇 차례가 전부이고,
그마저도 정해진 조건 한 가지만 확인하고 끝납니다.
단진자의 길이를 바꿔 볼 수도, 반응의 온도를 올려 볼 수도 없습니다.

그래서 **조건을 직접 바꿔 보고 결과가 어떻게 달라지는지 눈으로 확인할 수 있는
웹 과학 시뮬레이션**을 만들기로 했습니다. 목표는 세 가지입니다.

**첫째, 변수를 직접 조작하게 한다.**
21개 시뮬레이션에 총 76개의 조작 변수를 두었습니다. 화면이 "온도를 올리면
평형 상수가 달라진다"고 설명한다면, 그 온도를 반드시 만질 수 있어야 합니다.
설명만 있고 조작할 수 없는 값은 개발 과정에서 전부 찾아내 슬라이더로 열었습니다.

**둘째, 교육과정의 오개념을 정면으로 겨냥한다.**
시험에 자주 나오지만 학생들이 자주 틀리는 지점을 골라 시뮬레이션 주제로 삼았습니다.
산을 아무리 희석해도 pH가 7을 넘지 못하는 이유, 자극을 세게 줘도 활동전위의
크기가 변하지 않는 실무율, 피식자를 늘려 주면 정작 포식자가 늘어나는 개체 수
변화 — 글로 읽으면 외워야 할 예외지만, 직접 값을 바꿔 보면 당연한 결과가 됩니다.

**셋째, 준비물 없이 언제든 반복할 수 있게 한다.**
설치 없이 웹 브라우저만 있으면 되고, 학교의 저사양 PC에서도 즉시 실행됩니다.
실험 조건은 주소(URL)에 담기므로, 교사가 특정 조건을 링크 하나로 학생에게
전달할 수 있습니다.

여기에 질문·답변 커뮤니티와 AI 과학 도우미, 단계별 탐구 활동을 더해
**"시뮬레이션으로 확인하고, 막히면 묻고, 스스로 탐구까지 이어지는"** 흐름을
하나의 서비스에 담았습니다.

## 2. 개발환경 및 개발언어

### 개발 언어

| 구분 | 언어 |
|---|---|
| 프런트엔드 | HTML5, CSS3, JavaScript (ES2022) — 프레임워크·빌드 도구 없이 순수 구현 |
| 백엔드 | JavaScript (Node.js 22 런타임) |

### 개발 환경

| 구분 | 사용 기술 |
|---|---|
| 운영체제 | Windows 11 (WSL2 병행) |
| 호스팅·CDN | Azure Static Web Apps |
| 백엔드 | Azure Functions (서버리스, HTTP 트리거) |
| 데이터베이스 | Azure Cosmos DB (NoSQL) |
| 형상관리 | Git, GitHub |
| 배포 자동화 | GitHub Actions (main 브랜치 푸시 시 자동 배포) |
| 테스트 | Node.js 내장 테스트 러너 (`node --test`) |
| 생성형 AI | Upstage Solar Pro4 (OpenAI 호환 API) |

### 개발 보조 도구 — AI 코딩 활용

팀이 2명인 한계를 보완하기 위해 AI 코딩 도구를 적극적으로 활용했습니다.
Hermes 에이전트 환경에서 **Claude Code**를 주 개발 도구로, **Solar Pro4**를
자료 조사에, **Kimi K3**를 코드 작성에 나누어 사용했습니다.

다만 **AI가 만든 결과를 그대로 반영하지 않는 것**을 원칙으로 삼았습니다.
실제로 AI가 제안한 기능 8건 중 7건을 검증 과정에서 걸러냈습니다 —
이미 다른 값에 의해 결정되는 종속 변수를 조작 변수로 착각한 경우,
화학 반응식을 잘못 읽어 성립하지 않는 제안을 한 경우 등입니다.

물리·화학 계산식은 반드시 손계산과 대조해 확인했습니다.
예를 들어 화학 반응 시뮬레이션의 평형 상수는 반트호프 식으로 직접 계산한
값과 비교했고(25→75°C, 발열 반응에서 K가 2.000에서 0.110으로 감소),
전기화학의 네른스트 계수는 온도별 이론값과 소수점까지 일치하는지 확인했습니다.

또한 검증 코드를 신뢰하기 위해 **역검증**을 거쳤습니다.
테스트를 추가한 뒤 코드를 일부러 되돌려 그 테스트가 실제로 실패하는지 확인하고
원복하는 방식입니다. 이 과정에서 "통과하지만 아무것도 검사하지 않는 테스트"를
여러 건 찾아내 고쳤습니다.

## 3. 시스템 구성 및 아키텍처

### 3.1 전체 구조

별도의 상시 가동 서버 없이 **Azure Static Web Apps 한 서비스 위에서
프런트엔드·백엔드·데이터가 함께 동작하는 서버리스 3계층 구조**입니다.

```
                    사용자 (웹 브라우저)
                           │ HTTPS
   ┌───────────────────────▼────────────────────────┐
   │        Azure Static Web Apps (전역 CDN)         │
   │                                                │
   │  [1] 프레젠테이션 — 정적 자산                    │
   │      시뮬레이션 21종 (HTML5 Canvas + 순수 JS)    │
   │                    │ fetch(/api/*)             │
   │  [2] 애플리케이션 — Azure Functions (Node.js 22) │
   │      auth · posts · profile                    │
   │      reports · admin · llmChat  (API 30개)      │
   └───────────────────────┬────────────────────────┘
                           │
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
  ┌───────────┐   ┌──────────────┐   ┌──────────────┐
  │ [3] 데이터  │   │  OAuth 2.0   │   │  생성형 AI    │
  │ Cosmos DB │   │ Google·Kakao │   │ Solar Pro4   │
  │  (NoSQL)  │   │GitHub·Discord│   │              │
  └───────────┘   └──────────────┘   └──────────────┘
```

### 3.2 계층별 설계와 선택 근거

**[1] 프레젠테이션 — 프레임워크를 쓰지 않은 이유**

React·Vue 같은 SPA 프레임워크와 번들러를 의도적으로 배제했습니다.

- **Canvas 직접 렌더링**: 물리 시뮬레이션은 매 프레임 좌표를 다시 계산합니다.
  가상 DOM 비교 과정이 오히려 부담이 되므로, Canvas에 직접 그리는 방식이
  60fps 유지에 유리합니다.
- **빌드 과정 없음**: 소스 파일이 그대로 배포됩니다. 학교의 저사양 PC에서도
  번들 해석 없이 즉시 실행되며, 학생이 소스를 열어 학습 자료로 볼 수 있습니다.
- **URL로 상태 공유**: 실험 조건이 주소에 담겨, 링크 하나로 특정 조건을
  그대로 전달할 수 있습니다.

**[2] 애플리케이션 — 서버리스를 택한 이유**

수업 시간에 접속이 몰리고 그 외 시간에는 유휴 상태인 교육 서비스의 특성상,
요청 단위 과금과 자동 확장이 적합합니다. 상시 가동 서버와 비교해 운영 비용과
관리 부담이 모두 낮습니다.

기능별로 함수 6개를 두고, 공통 로직(세션·DB·크레딧·제재)은 `lib/`로 분리했습니다.

| 함수 | 담당 |
|---|---|
| `auth` | 소셜 로그인, 세션 발급·검증 |
| `posts` | 질문·답변·투표 |
| `profile` | 프로필, 약관 동의 |
| `reports` | 신고 접수 |
| `admin` | 운영·제재·크레딧 관리 |
| `llmChat` | AI 과학 도우미 |

**[3] 데이터 — 단일 컨테이너 설계**

Cosmos DB의 컨테이너 하나에 `type` 필드로 문서 종류를 구분합니다.
컨테이너 수에 비례하는 고정 비용을 피하기 위한 선택입니다.

이때 Cosmos DB에서 문서의 신원은 `(파티션키, id)` 조합이라는 점을 고려해,
한 사용자에게 여러 종류의 문서가 생기는 경우 id에 타입 접두사를 붙였습니다
(`user:<sub>`, `credit:<sub>`). 그렇지 않으면 종류가 다른 문서끼리 서로
덮어쓰게 됩니다.

### 3.3 인증 및 보안

**소셜 로그인** — Google·Kakao·GitHub·Discord 4종(OAuth 2.0)을 지원합니다.
비밀번호를 직접 보관하지 않아 유출 위험이 없고, 학생이 이미 쓰는 계정으로
가입 절차 없이 참여할 수 있습니다.

**세션** — JWT 라이브러리 대신 HMAC-SHA256 서명 쿠키를 직접 구현했습니다.

- `crypto.timingSafeEqual`로 서명 비교 — 일반 비교(`===`)는 불일치 지점에서
  즉시 종료되어 응답 시간 차이로 서명을 추측당할 수 있습니다(타이밍 공격)
- `httpOnly` — JavaScript가 쿠키를 읽지 못하게 하여 XSS로도 세션 탈취 불가
- `secure`, `sameSite: Lax` — HTTPS 전용 전송 및 CSRF 완화

**보안 헤더** — CSP(`default-src 'self'`)로 외부 스크립트 실행을 차단하고,
X-Frame-Options(클릭재킹), X-Content-Type-Options(MIME 스니핑) 등을
전역 적용했습니다.

### 3.4 생성형 AI 연동

AI 과학 도우미는 Upstage **Solar Pro4**를 사용합니다. OpenAI 호환
엔드포인트라 `openai` 패키지에서 주소만 교체해 연동했고, 의존성이 늘지 않았습니다.

교육 서비스에 필요한 방어 장치를 함께 구현했습니다.

1. **프롬프트 인젝션 2단계 대응** — 입력을 정제해 조용히 통과시키는 *완화*와,
   명백한 공격 의도를 가려내 차단하는 *탐지*를 분리했습니다. 호기심에
   시험해 본 학생까지 막지 않기 위한 구분입니다.
2. **크레딧 제도** — 토큰 사용량을 크레딧으로 환산해 차감하고 주기적으로
   충전합니다. 비용 폭증과 남용을 함께 억제합니다.

### 3.5 배포 및 검증

```
로컬 개발 → git push (main) → GitHub Actions → Azure 배포
                                    │
                          node --test (테스트 304개)
```

`main` 브랜치 푸시 시 자동으로 배포되며 약 1분 40초 내에 반영됩니다.
정적 파일과 백엔드 함수가 함께 배포되므로 프런트와 API 버전이 어긋나지 않습니다.
